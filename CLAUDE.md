# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

This is a team repo for the ArtTechHack 2026 hackathon. `brainstorm.md` holds the team's shared ideation notes. The active client is the WebXR app in `web/`. The earlier Unity client in `unity/` is kept for reference but is no longer the target platform. The backend isn't in the repo yet.

## Stack

- **Client:** WebXR app in `web/`, built with three.js (plain JavaScript, ES modules) and Vite. It targets the Meta Quest 3 browser and runs as an `immersive-ar` (passthrough) session.
- **Object recognition:** MediaPipe Tasks Vision (`@mediapipe/tasks-vision`, pinned to 0.10.14) with the EfficientDet-Lite0 model (80 COCO classes). It runs on the CPU delegate in the page. The wasm files and the model are fetched from jsdelivr and Google Storage at runtime, so the headset needs internet access.
- **Backend:** a separate service that handles the AI requests. The client talks to it using OMT.

## Web client (`web/`)

Commands, run from `web/` (needs Node ≥ 20.19; on NixOS use `nix shell nixpkgs#nodejs_22`):
- `npm install`: install dependencies
- `npm run dev`: start the HTTPS dev server on the LAN (port 5173)
- `npm run build`: production build into `dist/`

There are no tests or linter yet.

- WebXR requires a secure context. `vite.config.js` uses `@vitejs/plugin-basic-ssl` (a self-signed cert) and `host: true`, so the headset can open `https://<computer-ip>:5173`. The headset has to accept the certificate warning once.
- `src/main.js` holds the scene: the gaze dot, the label for the object being looked at, and a camera-attached HUD panel showing the camera image with detection boxes. The renderer uses three's default `local-floor` reference space, so y = 0 is the physical floor and -z is forward.
- `src/detector.js` opens the passthrough camera with `getUserMedia` (Quest 3/3S, Horizon OS v76+, "headset cameras" permission) and runs the detector on its own timer, about 4 times a second. The permission prompt can't appear inside an immersive session, so the page's "Enable camera" button has to be pressed before **Start AR**.
- **Asking the LLM:** whatever you look at for `CONFIG.dwellMs` (1 s) starts a narration. That's a box, or the whole scene when no box is under the gaze (`CONFIG.describeScene`). A crop from the full-resolution camera picture (384 px) goes to llama-server (`src/llm.js`, proxied at `/llm/*` → `127.0.0.1:8080`). The model keeps talking in short streamed turns for as long as the gaze stays. The first turn answers from the picture alone; later turns may call a `web_search` tool, served by the Vite plugin in `vite.config.js` at `/search?q=` (it scrapes DuckDuckGo's HTML page). Settling on a new target for `CONFIG.switchMs` (1.5 s) aborts the request and starts over; the sentence being spoken finishes first and the queued ones are dropped. A box the tracker loses and re-finds (same class, overlapping) counts as the same object. Sentences are spoken as they arrive through the Kokoro TTS (`src/voice.js`): each narration has its own voice, with a Web Audio gain and stereo panner. Pan follows how far left or right of the gaze centre the box is; volume follows the box size and its distance from the centre. With the stimuli slider (`control.html`) at 50% or more, the biggest other shown boxes get their own narrations at the same time (up to 2 at 50–79%, 3 at 80% and above). On the flat screen, "looking at" means the centre of the picture.
- **Eye tracking:** Quest 3 has no eye-tracking hardware, and the Quest browser doesn't expose eye gaze to WebXR (not even on Quest Pro). The "gaze" dot is head gaze: the centre of the view, placed on real surfaces through WebXR `hit-test`, or 1.5 m ahead if there's no hit. The looked-at object is the smallest detection box containing the camera image centre, which is only approximate because the passthrough camera sits offset from the eyes. Real eye tracking would need a Quest Pro with a native (Unity/OpenXR) app.

## TTS service (`tts/`)

- This is a local Kokoro text-to-speech server (Python, FastAPI, kokoro-onnx on the CPU), managed with uv. Run `./setup.sh` once (it targets Fedora and uses `dnf`), then `uv run server.py`. It listens on `127.0.0.1:8880`.
- The Vite dev server proxies `/tts/*` to it, so the HTTPS page never makes mixed-content requests. `web/src/tts.js` exports `speak(text, options)`, which plays the streamed PCM through Web Audio.
- On NixOS, the onnxruntime wheel needs `libstdc++` on `LD_LIBRARY_PATH` (or nix-ld).

## Unity project (`unity/`, inactive)

- Only `Assets/`, `Packages/manifest.json`, and `ProjectSettings/` are source; Unity generates everything else (see `unity/.gitignore`). Commit the `.meta` files Unity creates next to assets.
- The test scene `Assets/Scenes/BallTest.unity` is generated by `Assets/Editor/BallSceneBuilder.cs`. It's built automatically on the first editor load if missing, and can be rebuilt via the menu **ArtTech > Rebuild Ball Test Scene**. Change the builder rather than hand-editing that scene, until the team starts editing it in the editor for real.
- `Assets/Scripts/XRFloorOrigin.cs` requests floor-level tracking, so world y = 0 is the physical floor.
- The developer machine runs NixOS with the nixpkgs `unityhub` package. Launch editors from the Hub so they run inside its FHS environment.

## Challenge

The team is working on **Challenge 03 – Spatial AI & The Mind**: build an interactive system, generative tool, game, or VR/XR experience using Gaussian splatting and eye-tracking, with a focus on the human mind and spatial decision-making.

Recurring themes in the brainstorm that should guide implementation choices:
- Surveillance and vulnerability: gaze and movement tracking made visible to the participant.
- Two-person setup: one person in VR, another person controlling or observing.
- Generative rather than hardcoded: the participant can tune parameters live, such as the tracking intensity via a slider.
- Moral neutrality: the experience should let participants form their own feelings instead of telling them what to feel.
- Candidate tech mentioned so far: ml5.js and open-source hand/body/pose tracking models, plus immersive sound.
